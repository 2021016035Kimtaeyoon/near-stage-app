# NEAR:STAGE

공연할 곳이 없는 아티스트와 손님이 필요한 소규모 공간을 연결하고, 그렇게 만들어진
공연을 지도로 관객에게 보여주는 서비스입니다.

**완전 무료입니다.** 결제·수수료·예약금·정산 기능이 아예 없습니다. 개런티는 호스트와
아티스트가 직접 정하고 공연 당일 현장에서 정산하며, 플랫폼은 대금에 관여하지 않습니다.

---

## 실행

```bash
npm install
npm run dev
```

`.env.local` 이 필요합니다. 없으면 화면은 뜨지만 데이터를 못 읽습니다.

```bash
VITE_SUPABASE_URL=https://<프로젝트>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon public 키>
VITE_KAKAO_REST_API_KEY=<카카오 REST API 키>
VITE_KAKAO_JS_KEY=<카카오 JavaScript 키>
VITE_SITE_URL=http://localhost:5250
```

> **anon key 는 프론트에 노출되는 것이 정상입니다.** 보안은 RLS(행 수준 보안)가
> 담당합니다. `service_role` 키는 절대 프론트에 넣지 마세요 — 들어가는 순간 RLS 가
> 전부 무력화됩니다.

기타 명령어:

```bash
npm run build      # 프로덕션 빌드 (tsc --noEmit 포함)
npm run typecheck  # 타입체크만
npm run lint       # ESLint
```

배포는 [docs/DEPLOY.md](./docs/DEPLOY.md) 를 보세요.

## 데이터는 전부 실제입니다

목데이터가 없습니다. `src/store/emptyData.ts` 는 "아직 아무것도 불러오지 않은 상태"의
빈 값만 정의하고, 화면은 `src/hooks/use*.ts` 의 데이터 훅에서 읽습니다.

```
Supabase (Postgres + RLS + Realtime + Storage + Auth)
   │
   ├── v_public_shows  ─── 지도·목록·상세 (승인된 공간·팀의 공연만)
   ├── v_clip_feed     ─── 클립 피드 (좋아요·댓글 수 집계 포함)
   └── 나머지 표         ─── RLS 가 "누가 무엇을 볼 수 있는지"를 결정
```

### 보안의 원칙

**프론트에서 막지 않고 DB 에서 막습니다.** 화면의 조건문은 헛걸음을 줄이기 위한
것이고, 실제 차단은 RLS 정책이 합니다.

- `shows` 에는 **INSERT 정책이 없습니다.** 공연은 `fn_accept_application`
  (security definer)과 KOPIS Edge Function(service_role)만 만들 수 있습니다.
- 좋아요·팔로우·참석·알림 **행은 본인 것만** 읽힙니다. 화면에 필요한 "N명"은
  뷰가 집계해서 공개합니다.
- 지원서는 낸 팀과 받은 호스트만 봅니다. 신고는 신고자와 운영자만 봅니다.
- **위치 좌표를 서버로 보내지 않습니다.** 브라우저 안에서 거리 계산에만 쓰고
  저장하지 않습니다 (`useViewerLocation`).

### 매칭이 도는 자리

호스트가 지원자를 수락하면 `fn_accept_application` 한 번에 일곱 가지가 트랜잭션으로
일어납니다.

1. 이 지원 수락 → 2. 같은 글의 다른 지원 자동 거절 → 3. 구인글 마감 →
4. **공연 생성** → 5. 슬롯 잠금 → 6. 알림 3종 → 7. 대화방 생성

프론트에서 순서대로 부르면 중간에 실패했을 때 "공연은 만들어졌는데 슬롯은 안 잠긴"
상태가 남습니다. 그래서 DB 함수입니다.

## 프로젝트 구조

```
src/
  config/     전역 상수 (brand.ts), 탭 구성 (nav.ts), 약관 본문 (legal.ts)
  lib/        순수 유틸 — 날짜, 거리, 장비 대조(needMatch), 업로드, 공유, 클립 임베드
  hooks/      데이터 계층. 화면은 여기서만 데이터를 읽습니다
  store/      zustand — 필터·테마 같은 화면 상태. 데이터는 여기 두지 않습니다
  components/ 공용 UI(ui/), 카드(cards/), 지도(map/), 앱 셸(shell/)
  screens/    audience/ owner/ performer/ host/ artist/ admin/ legal/ common/ desktop/
  routes.tsx  라우트 (HashRouter)

supabase/
  migrations/ 0001~0016. 번호순으로 실행합니다
  functions/  sync-kopis (KOPIS 공연 수집), kakao-oidc (카카오 로그인 토큰 교환)
  tests/      rls_test.sql — RLS 정책 8개 검증
```

`★` 로 시작하는 주석은 "왜 이렇게 했는지"를 적은 것입니다. 그 자리를 고치기 전에
읽어주세요.

## 임의로 결정한 사항

스펙에 없거나 여러 해석이 가능해서 제가 정한 것들입니다. 바꾸고 싶으면 말씀해주세요.

### 데이터·표시

- **`ticketPrice` 를 쓰지 않습니다.** 우리 무대는 참가비가 없고, 등록 공연(KOPIS)은
  가격이 `"R석 70,000원 / S석 50,000원"` 처럼 자유 문장입니다. 파싱해서 숫자로 만들
  이유가 없어서(결제를 하지 않으므로) 원문(`price_note`)을 그대로 보여줍니다.
- **가격 필터를 없앴습니다.** 모든 공연의 `ticketPrice` 가 0 이라 필터가 아무것도
  걸러내지 못했습니다.
- **장르를 모르는 공연은 태그를 달지 않습니다.** 예전에는 목록에 없는 장르를 전부
  '연극'으로 끼워 넣어서, 오케스트라 정기연주회가 '연극'으로 표시됐습니다.
  틀린 라벨보다 원본 표기(`genre_raw`)를 그대로 보여주는 게 맞습니다.
- **공연 종료 여부를 시간으로 판단합니다.** `shows.status` 를 크론으로 `ended` 로
  바꾸는 방식은, 크론이 한 번 실패한 날 아무도 리뷰를 못 쓰게 만듭니다. 시계가 이미
  아는 것을 크론에 의존할 이유가 없습니다. `status` 는 취소처럼 사람이 정하는 일에만
  씁니다.

### 성과 리포트

- **"예상 추가 집객" 같은 추정치를 만들지 않습니다.** 공연이 없던 날의 방문객 수를
  알 방법이 없습니다. 알 수 없는 값으로 만든 숫자는 사장님이 그걸 근거로 결정을
  내리게 만들어서, 없는 것보다 나쁩니다. 실제 방문객은 호스트가 직접 적습니다
  (`show_reports`).
- **정산 화면을 만들지 않았습니다.** 개런티는 현장에서 직접 주고받는 돈이라 우리가
  기록할 근거가 없습니다. 있는 척하면 분쟁이 우리에게 옵니다.

### 슬롯·매칭

- **슬롯은 요일 반복 규칙이 아니라 구체적인 날짜입니다.** 규칙만 저장하면 "그 주는
  사정이 있어 못 해요"를 표현할 방법이 없습니다. "매주 반복"은 그 자리에서 몇 주치
  행을 실제로 만들고, 만든 뒤에 한 주씩 따로 닫을 수 있습니다.
- **장비 대조에서 못 읽은 항목은 "직접 확인"으로 남깁니다.** 충족으로 처리하면 당일
  현장에서 사고가 나고, 미충족으로 처리하면 멀쩡한 팀이 걸러집니다. 둘 다 거짓말이라
  사람이 보게 넘깁니다 (`lib/needMatch.ts`).
- **공간은 자동 승인, 팀은 운영자 확인.** 주소는 기계가 확인할 수 있지만 팀 실력은
  아닙니다. 단, 자동 승인은 "등록한 사람이 그 가게의 권한자인지"를 확인하지 못합니다.
  그래서 운영자가 사후에 내릴 수 있는 경로를 남겨뒀습니다.

### 클립

- **영상 파일 업로드를 받습니다** (원래는 링크만 받을 계획이었습니다). 업로드를 받는
  순간 우리가 저작물을 호스팅하는 주체가 되므로, 60초·30MB 제한을 브라우저에서 먼저
  막고 운영자가 신고받은 클립을 지울 수 있게 정책을 열어뒀습니다.
- **인스타그램·틱톡 링크는 앱 안에서 재생하지 않습니다.** 그쪽이 자동재생 임베드를
  제공하지 않습니다. 검은 화면을 띄우느니 있는 그대로 말하고 원본으로 보냅니다.
  유튜브·비메오는 임베드로 재생됩니다.
- **클립 좋아요는 DB 에 저장합니다** (예전에는 화면 로컬 상태였습니다). 앱을 닫으면
  사라지고 남에게도 안 보여서, 숫자가 0에서 안 움직였습니다.

### 로그인

- **카카오·구글만** 지원합니다. 이메일 가입은 Supabase 무료 플랜의 메일 발송이
  시간당 2~4통이고 스팸함으로 가서, 비밀번호 재설정이 사실상 불가능합니다.
  재설정을 못 주면서 비밀번호를 만들게 하는 건 안 만드는 것보다 나쁩니다.
  SMTP(Resend 등)를 붙인 뒤에 추가하는 게 맞습니다.
- **카카오 로그인은 우리 authorize URL 을 직접 씁니다.** Supabase 의 카카오 제공자가
  `account_email` 을 scope 에 강제로 넣는데, 비즈 앱이 아니면 그 동의항목을 켤 수
  없어 KOE205 로 막힙니다. Edge Function(`kakao-oidc`)에서 code→id_token 을 교환해
  `signInWithIdToken` 으로 들어갑니다.

### 그 외

- **주소→좌표 변환은 카카오, 실패하면 OpenStreetMap.** 카카오 JavaScript 키는
  사이트 도메인을 **하나만** 등록할 수 있어서, 등록되지 않은 곳에서는 401 이 납니다.
  그때 조용히 실패하지 않고 OSM 으로 넘어갑니다(정확도가 조금 낮습니다).
- **예매 화면(BookingFlow)을 지웠습니다.** 결제·좌석지정·QR 티켓이 없으니 예매라는
  단계 자체가 존재하지 않습니다. "참석 예정"은 호스트가 대략 몇 명 오는지 알기 위한
  숫자이고, 좌석을 보장하지 않는다고 약관에도 적었습니다.
- **약관·개인정보처리방침 본문은 `src/config/legal.ts` 에** 있습니다. 문서는 앱이
  실제로 하는 일과 한 글자도 어긋나면 안 되므로, 기능을 바꾸면 이 파일도 같이
  고쳐야 합니다.
